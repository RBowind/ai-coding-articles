## 全链路交付：新建与存量共用闭环

1. **需求**：用户价值、验收条件、边界
2. **设计**：业务/技术契约与风险
3. **编码**：AI 探索 → 计划 → 小步实现；人工审 diff
4. **测试**：按风险验证行为与契约
5. **发布**：渐进上线，预设停止与恢复条件
6. **监控**：SLO、错误信号和用户反馈进入下一轮需求

**共用产物**：需求与契约、变更差异、验证证据、发布记录。

**原则**：同一闭环，不同起点与风险护栏；AI 自主度随验证能力和变更风险调整。

两条路径的差异只在入口：

- **新建路径**：从目标出发，先立规范、测试和质量基线。
- **存量路径**：从真实行为出发，先建基线、影响面和兼容边界。
- **关键联动**：新建上线后即成存量；前期的契约、测试、CI、观测和 runbook 是后续维护资产。

这也是为什么「高效交付」不等于「快」：每一步都留下可核查的产物，下一轮才能从监控信号接着走，而不是从零重建信任。

## 新建项目怎么做｜从 0 到可发布

**主案例**：新订单/履约服务的第一条垂直切片；与存量案例共用订单域。
**贯穿要求**：每节留一张「交付证据」截图，展示决定和结果，不只展示工具界面。

### 1. 定义目标与验收

- PRD/UI design：用户流程、状态、验收标准、非目标
- 未决业务问题显式列出，避免让 AI 补全产品决定

### 2. 写清业务与技术契约

- 业务 Spec + TechSpec：领域模型、API/事件、数据、错误、安全、SLO
- 记录关键假设与架构决策；避免为未知需求过度设计

### 3. 搭建可交付骨架

- 约定目录/模块、可复现的本地启动与测试命令
- 从第一条切片建立 CI、lint/type/security、日志/指标和部署通路
- 给 agent 准确上下文与最小必要权限

### 4. 拆解并小步实现

- SDD：澄清 → Spec → Tickets → 实施；grill-with-docs / to-spec / to-tickets / implement 仅作工具例子
- TDD + 垂直切片：每步都有验收条件和验证命令
- AI 给出计划、改动和验证证据；人工审业务语义与 diff

### 5. 建分层验证

- 单测/集成/契约/BDD/E2E 按风险组合；Ginkgo / Cucumber 仅作框架例子
- Mutation test 检查断言质量；优先关键路径，不机械追覆盖率

### 6. 设 CI 质量门

- lint/type/test/security scan，检查须稳定、快速、可复现
- AI code/test review 做补充，不能代替自动检查和人工审查
- coverage 是风险信号，不一刀切要求 >90%；按关键路径设阈值再逐步收紧

### 7. 发布、观测与反馈

- 从早期准备灰度/开关、SLO/错误指标、告警、runbook 和回滚
- 线上信号和用户反馈回到下一轮需求，不以「合并代码」为交付终点

### 8. HOTL 与 Agent 自主度

- 作为第 5 讲引子：明确什么条件下可以从逐步确认提升到监督式运行
- 前提：可靠测试、清晰任务边界、最小权限、可观测动作和恢复能力

> 转入存量：上线后，契约、测试、CI、观测和 runbook 就是持续演进的基线；存量章节再讲如何先确认真实现状与兼容约束。

## 存量项目怎么做｜从陌生仓库到安全交付

**主案例**：老订单服务新增履约状态，兼容旧 API 与历史数据；每节留一张证据截图。
**本章目标**：在真实现状与兼容约束下，完成一项可验证、可停止、可恢复的变更。

### 1. 先建基线

- 固定 commit、环境、启动/测试命令与耗时
- 记录既有失败/不稳定项，区分基线和本次回归
- 使用安全开发环境、最小权限与脱敏数据
- 没有 CI 时，先建一条稳定、便宜的自动检查，不急着铺完整流水线

### 2. 看清现状

- 从入口追链路：业务 → DB/API/消息 → 消费方 → 部署与配置
- wiki、zread、graphify 是候选地图；对照源码/真实链路抽样验边，未知项显式记录
- 查 owner、SLO、数据边界、改动热点；用 `git log -S` / `git log -L` 追「为什么」
- 单体/多服务/事件驱动决定影响面与验证方式：HTTP 看 OpenAPI，消息看事件契约
- 输出系统图、证据和未知项清单

### 3. 圈定本次变化

- 分类：修 bug / 新需求 / 重构 / 子系统替换
- 分开写当前行为、目标行为、不变量与验收条件
- 追读写路径及 API/事件/DB/配置/权限/消费者，标出兼容对象和风险
- 练习目标：一小时内形成可验证的影响面初稿，未知项不隐藏

### 4. 先建安全网

- 特征测试固定可观察现状，不代表认可 bug；需求测试验证目标行为
- 按风险覆盖改动点与契约/关键路径，不机械追求全覆盖
- AI 先总结现有行为并提测试；在未改代码上运行，人工核对断言；测试与修复分开提交

### 5. 选最小可停的切法

- 局部改动 → 抽接口/适配层替换 → feature flag 渐进切换 → 只读影子验证 → 绞杀者迁移
- 每种切法写清适用条件、停止阈值、回退或前向修复方案
- 影子流量不可重复副作用；双写要有一致性校验与补偿方案
- 大爆炸重写是高风险例外，先拆出可停点，不当成默认切法

### 6. AI 小步实现

- 先只读探索：给出文件/符号证据、假设和未知；人工抽样核验
- 约束改动范围、行为、不动边界和验证命令；一次一个垂直切片
- 审 diff、依赖与迁移；先跑定向测试，再跑相关全量检查
- 不接受无解释的「顺手重构」，业务/数据/发布决策由人确认

### 7. 数据与发布

- expand → backfill → verify → switch → contract；兼容新旧版本，回填幂等、分批、可校验
- 双写不是默认方案；明确一致性、补偿与失败重试
- DB 操作按目标版本核验锁与失败行为；PG 默认值加列、并发建索引要讲清适用条件
- 灰度/开关/影子对照：定义指标、停止条件和观察窗
- 应用回滚 ≠ 数据回滚；明确逆向迁移、前向修复或备份恢复

### 8. 验证、收口与交接

- 验收用例 + 运行指标；确认无越界 diff
- 清理开关/死代码需调用图、覆盖或运行证据，并确认 owner
- 更新项目实际维护的测试/架构/迁移/回滚文档；AGENTS.md 仅在项目使用且内容确有变化时更新
- 留下复用包：基线、系统与影响图、测试结果、发布/回滚结论
- 回流工程资产：渐进补齐契约、测试、CI、观测和文档，不以一次性全量重构为目标

## 两条路径放在一起看

| 维度 | 新建项目 | 存量系统 |
| --- | --- | --- |
| 起点 | 目标、验收条件与边界 | 真实行为与可复现基线 |
| 第一件事 | 立规范、契约和质量基线 | 建基线、影响面与兼容边界 |
| 主要风险 | 需求未决、让 AI 补全产品决定、过度设计 | 兼容破坏、数据不可回滚、隐藏的未知项 |
| 验证重点 | 分层测试 + CI 质量门 | 特征/需求测试 + 兼容契约 + 灰度与影子对照 |
| 收尾产出 | 上线信号进入下一轮需求 | 复用包与工程资产回流 |

**关键联动**：新建上线后即成存量，契约、测试、CI、观测和 runbook 就是后续演进的基线；存量章节再讲如何先确认真实现状与兼容约束。

**总原则**：同一闭环，不同起点与风险护栏；AI 自主度随验证能力和变更风险调整。HOTL（监督式运行）的前提是可靠测试、清晰任务边界、最小权限、可观测动作和恢复能力。
